## Архитектура интерфейсов

- Базовый стек: Django, PostgreSQL, Django Templates, Django Forms/ModelForms, стандартная Django Admin, обычный CSS и Vanilla JavaScript. Приоритет — встроенные возможности Django, минимум зависимостей и простота поддержки.
- Публичный сайт, кабинет и анкеты — серверные шаблоны; формы работают через стандартные Django Views с GET/POST, серверной валидацией и сохранением. Динамические поля строятся на сервере по настройкам фестиваля. После ошибки показывай введённые значения и ошибки, POST защищай CSRF.
- Делай современный, визуально привлекательный, адаптивный интерфейс по фирменному стилю РИ-феста. Используй общие шаблоны, переиспользуемые элементы и структурированные CSS-файлы с переменными темы; не подменяй дизайн стандартным видом форм.
- Проживание, питание и общий итог мгновенно пересчитываются без перезагрузки обычным JavaScript; браузерный расчёт предварительный, окончательный — на сервере. Для браузерного расчёта используй целые копейки.
- Организаторы работают в стандартной Django Admin: ModelAdmin, list_display, list_filter, search_fields, ordering. Финансовые колонки, сортировка и фильтры по вычисляемым суммам используют согласованные с billing ORM-выражения, аннотации и специализированные фильтры, без N+1 и повторного полного расчёта каждой строки; архив — из снимков. Специальные формы, шаблоны, CSS и JavaScript добавляй точечно, не создавай свою панель с нуля.
- Отдельные SPA и REST API не планируются. Vue, Alpine.js, HTMX, Tailwind CSS, Django Unfold и Django REST Framework не подключай по умолчанию. Если задача плохо подходит выбранной архитектуре, укажи конкретную причину и предложи альтернативу для согласования. При существенном усложнении анкеты допустимо предложить локальный Vue в Django Templates; Unfold — при недостатках удобства или оформления Admin. Самостоятельно архитектуру не меняй.

## Работа с задачами
- Реализуй только задачу с указанным ID из плана. Другие задачи не выполняй заранее без прямой просьбы.
- Давай фактические результаты проверок. Если команда не выполнялась, укажи причину; не утверждай, что тесты прошли без выполнения.
- Пиши тесты на правила, которые меняешь. Не удаляй падающие тесты ради зелёного результата.
- Если требуется неоговорённое решение в оплатах, архивах, правах и уведомлениях — остановись и спроси, не выбирай произвольно.
- Не делай ненужных зависимостей, глобальных рефакторингов, сложной SPA или дополнительных бизнес-возможностей вне задания.
- Для задач интерфейса проверяй GET/POST и ошибки форм, мгновенный пересчёт в браузере, финансовые колонки Admin, поиск, сортировку, совместные фильтры и отсутствие N+1. Проверки кода не заменяют браузерную проверку.

## Git и отображение изменений

- Не выполняй commit, push, merge, rebase, создание или удаление веток без явной просьбы. Просьба составить коммит означает изучить все фактические изменения и предложить английское сообщение Conventional Commits, а не выполнять git commit.
- Любое создание, редактирование, переименование или удаление файла проекта выполняй только встроенным apply_patch, отдельно для каждого файла. Не объединяй такой вызов с чтением, проверками или другими инструментами; не записывай изменения через терминал, IDE-инструменты или форматтеры с перезаписью.

## Инварианты
- Один пользователь может иметь несколько отдельных анкет.
- Сумма оплаты одна; организатор может **задать**, **прибавить** или **вычесть** без объяснений. Не вводи отрицательный paid.
- Отметка «Взнос оплачен» ставится и снимается **только вручную организатором**; сумма при фиксации сохраняется.
- Изменение цен проживания/питания влияет на все заявки текущего фестиваля, но не на размер внесённой оплаты; архив нельзя изменять.
- Никакая сумма из браузера не считается достоверной: финальный расчёт на сервере.
- Подписки организаторов на уведомления индивидуальны; недоступная интеграция не имитируется.
- Секреты не коммитить. В тестах использовать только синтетические данные, не реальные анкеты или персональные данные.
