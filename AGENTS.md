# Инструкции для Codex: РИ-фест

## Источники

Сначала найди в [плане](docs/plan.md) только нужную задачу и прочитай её описание. По заголовкам или поиску открой лишь связанные разделы [ТЗ](docs/roadmap.md) и [архитектуры](docs/architecture.md), затем изучи затрагиваемый код. Не загружай документы целиком и не читай связанные тесты заранее: найди их после определения изменяемого поведения. Расширяй чтение только при обнаружении зависимости или противоречия. Повторно используй контекст текущего разговора, перепроверяя изменившиеся файлы. Материалы фестиваля нужны только для задач контента и оформления.

Команды запуска и выборочных проверок — в [README](README.md). Явные указания пользователя имеют приоритет.

## Разработка

- Выполняй запрошенную задачу; следующие этапы и посторонние рефакторинги не начинай без просьбы.
- Используй Django Templates, Forms/ModelForms, стандартную Admin, обычный CSS и JavaScript. Сохраняй фирменный адаптивный дизайн, общие шаблоны и переменные темы. Отдельные SPA и REST API не планируются; новые зависимости и изменения архитектуры сначала обоснуй и согласуй.
- Бизнес-правила описаны в ТЗ. Не выбирай самостоятельно неоговорённые решения об оплатах, архивах, правах и уведомлениях — уточни их у пользователя.
- Запускай проект и проверки через Docker. Python задан в Dockerfile, зависимости — в requirements.txt. Локальное окружение PyCharm без необходимости не меняй.
- Для разработки подключай `compose.dev.yaml` по README: исходники доступны без пересборки. Пересобирай образ при изменении зависимостей или Dockerfile; новые миграции применяй отдельно. Worker и единственный Beat перезапускай при изменениях используемого ими кода или настроек.
- Не добавляй секреты в Git. Для тестов используй только вымышленные данные.

## Интерфейс и тексты

- Сохраняй цветовую гамму сайта: тёплый светлый фон, спокойные нейтральные поверхности, тёмный текст и акцент; проверяй также тёмную тему и контраст. Все переменные сайта и Admin хранятся в `static/css/theme.css`; основной цвет задаётся через `--color-accent`. Для Admin используй компоненты Unfold и общую поверхность `admin-panel`, чтобы блоки отличались от фона и имели адаптивную к теме границу.
- Выравнивай связанные поля и действия по общей сетке, отделяй разные операции и проверяй переносы на небольших экранах. Иконки действий должны иметь понятные подписи для клавиатуры и скринридеров.
- Подсказки пиши полными понятными фразами на русском языке: объясняй, что произойдёт, когда сохраняются изменения и что пользователь должен сделать дальше. Проверяй смысл текста по актуальным бизнес-правилам.

## Проверки

- Запускай минимальный набор проверок, который покрывает изменённое поведение. Не запускай все тесты, `check.py` или интеграционный профиль для локальной правки; полный набор нужен при завершении контрольной точки, общей инфраструктурной правке, подготовке выпуска или прямой просьбе пользователя.

  | Изменение | Проверки |
  |---|---|
  | Документация | Содержание и ссылки; без запуска приложения |
  | Текст, CSS, оформление шаблона | Изменённая страница в браузере; без новых Python-тестов, если поведение не меняется |
  | Форма, view, сервис | Тесты изменённого поведения и непосредственно связанных сценариев; Ruff для изменённых Python-файлов |
  | Модель, миграция | Связанные тесты, Django check и проверка миграций; PostgreSQL для ограничений и блокировок |
  | Общая инфраструктура, завершение контрольной точки | Полный `check.py` и соответствующие интеграционные проверки |

- Добавляй или меняй тест только для нового/изменённого бизнес-правила либо воспроизводимого дефекта. Не пиши тесты для текстов, простого оформления, очевидных мелочей, стандартного поведения Django или деталей реализации; не дублируй уже покрытый сценарий. Сохраняй существующие проверки прав, чужих анкет, архива, финансов и конкурентных операций, если правка их затрагивает.
- Для Python запускай относящиеся к правке тесты и Ruff только для изменённых Python-файлов; для моделей — также Django check и проверку миграций, PostgreSQL — когда затронуты ограничения или блокировки. Не повторяй успешную проверку без новых относящихся к ней изменений или нерешённой проблемы. Существующие тесты не удаляй ради ускорения и не удаляй падающие тесты ради успешного результата.
- Проверяй изменённый интерфейс в браузере. В результате перечисляй выполненные проверки и причины, если что-то не запускалось; выборочная проверка не означает, что прошла полная приёмка задачи.
- Для крупных браузерных изменений используй доступный скилл Playwright для браузерной приёмки.

## Git и отображение изменений

- Не выполняй commit, push, merge, rebase, создание или удаление веток без явной просьбы. Если просят составить коммит, изучи состояние Git и все фактические изменения, затем предложи сообщение на английском в формате Conventional Commits. Сам коммит не создавай.
- Файлы проекта создавай, редактируй, переименовывай и удаляй только встроенным apply_patch: один файл за вызов, без других операций в том же вызове. Не записывай правки через терминал, IDE-инструменты или форматтеры с перезаписью.
