
# РИ-фест

## Контекст
- Найди нужную задачу в [плане](docs/plan.md). Читай только связанные разделы [ТЗ](docs/roadmap.md), [архитектуры](docs/architecture.md) и затрагиваемый код.
- Не загружай документы целиком и не изучай тесты до определения затрагиваемого поведения. Расширяй поиск только по необходимости.
- Учитывай контекст разговора, перепроверяй изменённые файлы.
- Материалы фестиваля используй только для контента и оформления.
- Команды запуска и проверок — в [README](README.md).

## Разработка
- Выполняй только запрошенную задачу, без посторонних рефакторингов.
- Стек: Django Templates, Forms/ModelForms, Django Admin, CSS, JavaScript. Без SPA и REST API. Новые зависимости и архитектурные изменения сначала согласовывай.
- Не придумывай бизнес-правила по оплатам, архивам, правам и уведомлениям — сверяйся с ТЗ, при необходимости уточняй.
- Используй Docker и compose.dev.yaml согласно README. Не меняй локальное Python-окружение без необходимости.
- Пересобирай образ при изменении Dockerfile или зависимостей; миграции применяй отдельно. Перезапускай Worker и единственный Beat при изменении используемого ими кода или настроек.
- Не добавляй секреты в Git. Для тестов используй вымышленные данные.

## Дизайн
- Сохраняй фирменный адаптивный стиль: тёплый светлый фон, нейтральные поверхности, тёмный текст, акцентный цвет.
- Переменные сайта и Admin — в static/css/theme.css; основной цвет — --color-accent. Поддерживай светлую и тёмную темы.
- Для Admin используй Unfold и общую поверхность admin-panel с адаптивной к теме границей.
- Переиспользуй существующие компоненты и стили. Не создавай параллельную дизайн-систему.
- Группируй связанные поля и действия, обеспечивай читаемость, адаптивность, контрастность и доступность управления.
- Подсказки пиши понятными полными фразами на русском языке, объясняя последствия действий. Проверяй их по бизнес-правилам.

## Проверки
Выбирай минимальные проверки по типу изменения:

- Документация: содержание и ссылки, без запуска приложения.
- Текст/CSS/шаблоны: изменённая страница в браузере; Python-тесты не нужны без изменения поведения.
- Форма/view/сервис: связанные тесты и Ruff для изменённых Python-файлов.
- Модель/миграция: связанные тесты, Django check, проверка миграций; PostgreSQL при изменении ограничений или блокировок.
- Инфраструктура, контрольная точка, релиз: полный check.py и необходимые интеграционные проверки.

Дополнительно:
- Добавляй тесты только для новых или изменённых бизнес-правил и воспроизводимых дефектов. Не дублируй покрытие и не тестируй очевидное оформление или стандартное поведение Django.
- Сохраняй проверки прав, чужих анкет, архива, финансов и конкурентных операций при затрагивающих их изменениях.
- Не удаляй тесты ради успешного результата и не повторяй успешные проверки без причины.
- Проверяй изменённый интерфейс в браузере; затронутые темы и адаптивность — по необходимости.
- В результате перечисляй выполненные и пропущенные проверки. Не называй выборочное тестирование полной приёмкой.
