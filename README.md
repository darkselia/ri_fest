# РИ-фест

Сайт регистрации на Сибирский фестиваль ролевых игр «РИ-фест»: Django, PostgreSQL, серверные шаблоны и формы, Django Admin с оформлением django-unfold, обычные CSS и JavaScript.

## Документация и текущий объём

Реализованы аккаунты, несколько фестивалей, конструктор анкет, ответы, услуги и тарифные блоки платы по дате. Главная пока заглушка. Учёт внесённых денег, индивидуальные фиксации, архивные финансовые снимки, XLSX, редактируемый публичный контент и уведомления организаторов ещё не реализованы. Предварительная сумма анкеты не означает подтверждённую оплату.

## Подготовка один раз

1. В корне проекта создайте `.env` по образцу [.env.example](.env.example).
2. Заполните `DJANGO_SECRET_KEY`, `DB_PASSWORD` и `POSTGRES_ADMIN_PASSWORD`. Пароли приложения и администратора БД должны различаться. Значения со знаком `$` заключайте в одинарные кавычки.
3. Для локальной разработки оставьте `DJANGO_DEBUG=True` и почтовые настройки Mailpit.
4. Для доступа с другого устройства добавьте IP или имя Docker-хоста в `DJANGO_ALLOWED_HOSTS` (через запятую).

### Переменные окружения

Все переменные проекта приведены в [.env.example](.env.example). Compose подставляет значения из `.env` при создании конфигурации, а значения из окружения запускающей оболочки имеют приоритет. Django также читает `.env` при непосредственном запуске. После изменения настроек контейнеров выполните `docker compose -f compose.yaml -f compose.dev.yaml --profile dev-mail up -d`: `restart` и `start` не применяют новую конфигурацию.

| Переменная | Назначение и значение для Docker по умолчанию |
| --- | --- |
| `DJANGO_SECRET_KEY` | Обязательный секрет Django; используйте собственное случайное значение. |
| `DJANGO_DEBUG` | Режим отладки, `True` для разработки; вне разработки используйте `False`. |
| `DJANGO_ALLOWED_HOSTS` | Допустимые имена и IP через запятую: `localhost,127.0.0.1,[::1]`. |
| `DB_NAME`, `DB_USER`, `DB_PASSWORD` | База, роль и пароль приложения: `ri_fest`, `ri_fest` и обязательный пароль. |
| `POSTGRES_ADMIN_PASSWORD` | Обязательный пароль администратора PostgreSQL при инициализации тома. |
| `DB_HOST`, `DB_PORT` | Адрес PostgreSQL **из контейнера**: `db` и `5432`. Для внешней БД укажите её адрес и порт. |
| `DB_TEST_NAME` | Отдельная база PostgreSQL для тестов: `ri_fest_test`. Имя должно заканчиваться на `_test` и отличаться от `DB_NAME`. |
| `CELERY_BROKER_URL` | Адрес Redis из контейнеров приложения: `redis://redis:6379/0`. |
| `CONTENT_MEDIA_ROOT` | Абсолютный путь внутри контейнера к файлам страниц: `/var/lib/ri-fest/content`. Здесь же монтируется том `content_data`. |
| `EMAIL_HOST`, `EMAIL_PORT` | SMTP-сервер и порт из контейнера: `mailpit`, `1025`. |
| `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD` | Необязательные логин и пароль SMTP; по умолчанию пустые. |
| `EMAIL_USE_TLS`, `EMAIL_USE_SSL` | Режимы SMTP, оба по умолчанию `False`; одновременно включать нельзя. |
| `DEFAULT_FROM_EMAIL` | Адрес отправителя; пример — `no-reply@ri-fest.invalid`. |
| `DEV_WEB_PORT`, `DEV_DB_PORT`, `DEV_REDIS_PORT` | Внешние порты сайта, PostgreSQL и Redis: `8081`, `5432`, `6379`. |
| `DEV_MAILPIT_WEB_PORT`, `DEV_MAILPIT_SMTP_PORT` | Внешние порты интерфейса Mailpit и его SMTP: `8025`, `1025`. |

`DEV_*_PORT` используются только с `compose.dev.yaml` и меняют порт на компьютере, не порт внутри Docker. Например, при `DEV_DB_PORT=5433` приложение продолжает обращаться к `db:5432`, а клиент на компьютере — к `localhost:5433`. Порты публикуются на всех сетевых интерфейсах; ограничивайте доступ сетевым экраном.

При изменении `CONTENT_MEDIA_ROOT` Compose подключает тот же том к новому пути внутри контейнера; содержимое тома не переносится в каталог проекта. Путь должен быть абсолютным и доступным пользователю `app` для записи. При новом томе и нестандартном пути проверьте права тома: каталог вне подготовленного в образе `/var/lib/ri-fest/content` может потребовать отдельной настройки владельца. Не меняйте путь одновременно с удалением тома; резервируйте файлы вместе с базой.

## Dev: повседневная разработка

### Первый запуск

```powershell
docker compose -f compose.yaml -f compose.dev.yaml --profile dev-mail up --build -d
```

Команда собирает образ и запускает PostgreSQL, Redis, сайт, Celery worker, единственный Beat и Mailpit. Сервис `migrate` применяет миграции перед запуском приложения.

- Сайт: `http://<IP-компьютера>:8081/`; Django Admin: `http://<IP-компьютера>:8081/admin/`.
- Mailpit: `http://<IP-компьютера>:8025/`; SMTP для приложения и других устройств: <IP-компьютера>:1025`. 
- PostgreSQL: `<IP-компьютера>:5432` 
- Redis: `<IP-компьютера>:6379`.

### Следующие запуски

Если зависимости, Dockerfile и переводы не менялись, сборка не нужна:

```powershell
docker compose -f compose.yaml -f compose.dev.yaml --profile dev-mail up -d
```

Исходники подключены в `/app` только для чтения, Django перезагружается автоматически. После изменения зависимостей или Dockerfile повторите команду первого запуска с `--build`. Переводы в `locale/` также требуют пересборки: скомпилированный каталог Admin хранится вне `/app`.

Если контейнеры были только остановлены командой `stop`, продолжить их работу без пересоздания можно командой `start`, приведённой ниже.

При необходимости принудительно перезапустить только Django, сохранив контейнер:

```powershell
docker compose -f compose.yaml -f compose.dev.yaml restart web
```

После изменения фонового кода:

```powershell
docker compose -f compose.yaml -f compose.dev.yaml restart worker beat
```

После добавления миграций:

```powershell
docker compose -f compose.yaml -f compose.dev.yaml exec web python manage.py migrate --noinput
```

### Остановка и продолжение работы

Остановить существующие контейнеры, сохранив их и данные:

```powershell
docker compose -f compose.yaml -f compose.dev.yaml --profile dev-mail stop
```

Запустить те же контейнеры:

```powershell
docker compose -f compose.yaml -f compose.dev.yaml --profile dev-mail start
```

`restart` перезапускает существующие контейнеры, `up` создаёт или пересоздаёт их при необходимости, `down` удаляет контейнеры и сеть проекта. Обычный `down` сохраняет именованные тома; добавление `--volumes` удаляет и их данные.

PostgreSQL, Redis и расписание Beat хранятся в именованных томах. Изменение паролей в `.env` не меняет пароли уже созданных ролей PostgreSQL.

### Демо-данные

Команда сидирования требует явного режима. Все варианты сначала можно посмотреть без изменений, добавив `--dry-run`:
Режимы:
- `--mode reset --apply` очищает данные во всех Django-моделях текущей базы, затем создаёт демо-пользователей и фестивали. Разрешён только при `DJANGO_DEBUG=True`; схема и миграции остаются.
- `--mode add --apply` добавляет демо-пользователей и фестивали, не очищая существующие данные. Если демо-адрес уже занят, пользователь сохраняется и новые анкеты создаются на его аккаунте.
- `--mode refresh --apply` заменяет фестивали с названиями «РИ-фест: Первый ролевой», «РИ-фест 2027: Первый ролевой», «Северный ветер», «Северный ветер: игры у озера», «Мастерская миров» и «Осенние встречи». Удаляются все их анкеты и связанные поля и финансовые данные независимо от владельца; аккаунты и данные других фестивалей сохраняются. Демопользователи повторно используются. Фестивали определяются по названию, поэтому сначала проверьте `--dry-run`: он покажет ID, названия и число анкет, попадающих под замену.

Запуск выбранного режима:

```powershell
docker compose -f compose.yaml -f compose.dev.yaml exec web python manage.py seed_demo_data --mode refresh --apply
```

## Проверки

Для уже запущенного dev-окружения:

```powershell
docker compose -f compose.yaml -f compose.dev.yaml exec web python check.py
docker compose -f compose.yaml -f compose.dev.yaml --profile test run --rm tests
docker compose -f compose.yaml -f compose.dev.yaml exec web python manage.py makemigrations --check --dry-run
```

- `check.py`: Django check, pytest на SQLite в памяти, Ruff и проверка форматирования без перезаписи.
- Сервис `tests`: все сценарии с маркером `pytest.mark.postgres` на отдельной PostgreSQL-базе `DB_TEST_NAME` (по умолчанию `ri_fest_test`), Redis и SMTP через Mailpit. Набор охватывает аккаунты, фестивали, оплату и конкурентные операции с анкетами. Новые сценарии, которым нужен PostgreSQL, также помечайте этим маркером: профиль `test` подхватит их автоматически и подключит нужные зависимости.
- `makemigrations --check --dry-run`: проверка соответствия моделей и миграций без создания файлов.

Загруженные файлы информационных страниц хранятся в отдельном Docker-томе `content_data`, вне публичных staticfiles.
При резервном копировании сохраняйте этот том вместе с базой данных и проверяйте восстановление обоих компонентов.
Удаление тома удаляет загруженные файлы; пересоздание контейнера web их сохраняет.

Проверки выбираются по изменению согласно [AGENTS.md](AGENTS.md). Для правки документации приложение запускать не требуется; полный набор нужен при завершении контрольной точки и перед выпуском.

## Отступы и dev-линтер

Обычный запуск только проверяет форматирование и показывает diff, ничего не перезаписывая:

```powershell
docker compose -f compose.yaml -f compose.dev.yaml --profile dev-tools build lint
docker compose -f compose.yaml -f compose.dev.yaml --profile dev-tools run --rm lint
```

Можно проверить только изменённые файлы, передав их аргументами:

```powershell
docker compose -f compose.yaml -f compose.dev.yaml --profile dev-tools run --rm lint python tools/lint_format.py templates/admin/applications/edit.html static/js/admin_lists.js
```

Чтобы отформатировать все Django-шаблоны, JavaScript, CSS и Python-файлы проекта, добавьте `--write`:

```powershell
docker compose -f compose.yaml -f compose.dev.yaml --profile dev-tools run --rm lint python tools/lint_format.py --write
```

Полная проверка также показывает старые расхождения форматирования. Правила Python-кода
дополнительно проверяются командой `ruff check` в `check.py`.

## Почта и подтверждение email

Для настоящей отправки заполните SMTP-переменные из [.env.example](.env.example): сервер, порт, логин, пароль, TLS/SSL и адрес отправителя. TLS и SSL одновременно не включаются. После изменения `.env` повторите `up -d` для выбранного режима и отдельно проверьте доставку. При использовании внешнего SMTP Mailpit не требуется.

В `ri_fest/settings.py` настройка `EMAIL_VERIFICATION_REQUIRED=False` разрешает вход после регистрации без подтверждения email. При `True` новый аккаунт сначала подтверждает адрес. Эта настройка не зависит от DEBUG и не задаётся через env. Она также определяет порядок смены email: сразу либо после подтверждения нового адреса.
